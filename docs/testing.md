# 测试方法、覆盖范围与局限

`bash test/verify.sh` 是主入口。这份文档说明它到底测了什么、怎么测的、以及它证明不了什么。

## 测试环境

以下数字都是在一台 Linux 开发机上当场跑出来的：

| 项 | 实测值 |
|---|---|
| 操作系统 | Arch Linux（rolling），内核 7.3.4-arch1-1，x86_64 |
| JDK | OpenJDK 25（`javac 25.0.5.0.3`），字节码目标 Java 8（major 52） |
| Shell | GNU bash 5.3.20 |
| 被测电路 | `circuits/cpu-completed.circ`，335,320 字节 |

Windows / macOS 上没有实测过。脚本的路径全部相对化、classpath 分隔符会自动判断，
理论上跨平台没问题，但真出问题多半是 `java` 不在 PATH 或分隔符没对上。

## 测试方法

不开图形界面，也不靠人工点"模拟 → 单步"。所有测试都用 Logisim 自己的 Java API
加载 `.circ`、给引脚赋值、读输出、逐位比对 —— 走的和 GUI 打开电路是同一条代码路径
（`Loader.openLogisimFile` 加载、`Propagator` 做组合传播、`Clock.tick` 推进时钟），
所以"测试通过"和"在界面里能正常跑"是同一件事，不存在测试脚本自己另搞一套仿真的情况。

### 六节 36 项的分布

| 节 | 检查内容 | 项数 | 工具 |
|---|---|---|---|
| 一 | NPC 全部编码组合：`NPCOp` 000~111 × `Zero` 0/1 | 16 | `Vfy` |
| 二 | NPC 边界值：`Imm16` 负偏移、`Imm26` 顶端、PC 回绕 | 3 | `Vfy` |
| 三 | EXT：零扩展 / 符号扩展，含 `0x8000` 符号位起点 | 10 | `Vfy` |
| 四 | 顶层数据通路：第一条 `addi $s0,$zero,-1` 的 IR / RDin / RegWrite | 3 | `Vfy` |
| 五 | 整机推进 10 拍：PC 按 +4 前进，取到 `sw`、`addi` 并正确置写使能 | 3 | `Step` |
| 六 | 功能指纹：8 个子电路的输入输出关系与基准逐行比对 | 1 | `Fp` |

### 不在 36 项里的两项

它们要滚几十屏，塞进脚本里没法看，所以留成单独命令。

**1. 整机跑到底（224 周期）**

```bash
java -cp "simulator/logisim.jar:test" \
     Run "circuits/cpu-completed.circ" "单周期MIPS CPU" 3000
```

判据是**总周期数 224、停在 PC = 0x98**。模板程序是冒泡排序，静态 38 条、动态 224 条。
单周期一指令一周期，任何译码/扩展/写回错 → PC 跑飞或死循环 → 这个数立刻不对。

**2. 控制器穷举（4096 组）**

`OP[6] + Func[6]` 共 12 位，4096 组输入全跑一遍，把 14 条指令 × 9 个控制信号的 126 个取值
与布尔表达式逐条比对，约 6 秒。它针对的是译码逻辑，和上面六节覆盖的部件/整机是不同层面。

## 功能指纹：抓「静悄悄改坏」

前五节是硬编码期望值，只覆盖 NPC / EXT / 顶层 / 整机前十拍。如果改的是 `CTRL2`、`RF`、`GCN`
这些没写死用例的子电路，前五节一个都查不出来。

所以加了 `Fp`：对每个子电路，输入位宽不超过 12 位就**穷举**，否则用固定种子抽 256 组随机输入，
dump 成 `电路名 | 输入 -> 输出` 的文本表，与 `baseline.txt` 逐行 diff。

**改完版式（拖元件、走线、加 Tunnel）指纹完全不变；拖断一根线则整片输出全变。**
这就是判断"只动了外观"还是"动了逻辑"的依据。

## 测你自己的改版

```bash
bash test/verify.sh /任意路径/我的改版.circ
```

脚本会自动把文件搬进 `circuits/` 再测（否则找不到 jar），测完删掉。

全绿时会把当前文件存一份 `test/.last-good.circ`；改坏了它会打印覆盖回去的命令。

## 改了 Java 工具才需要

```bash
bash test/build.sh
```

`verify.sh` 发现没有 `.class` 或 `.java` 比 `.class` 新，会自动调它，正常不用手动跑。
字节码目标固定为 Java 8，保证别人用老 JDK 也能跑。

## 测试的局限

这套测试能证明"逻辑对"，但下面几条它证明不了。

1. **只是功能验证，不含时序**。Logisim 做的是功能仿真，不检查建立/保持时间、不计算关键路径
   延迟。所以"224 周期通过"只说明指令一条条执行正确，不代表这个结构能在真实 FPGA 上跑到
   某个时钟频率 —— 单周期 CPU 的关键路径本来就长（取指 → 译码 → 寄存器堆 → ALU → 访存 → 写回），
   实际最高频率远低于 Logisim 里看到的速度。

2. **224 是个聚合判据，不能定位**。它只回答"整体对不对"，错了不会告诉你是哪条指令、哪个信号。
   真要定位，得看控制器穷举表，或者用 `Step` 逐拍打印 PC / IR。

3. **整机只走到 8 条指令**。模板里那段冒泡排序没有用到 `sub / ori / lui / sltu / jal / jr`，
   这 6 条的整机通路一次都没被激活。它们的正确性是由控制器穷举测试单独保证的 —— 是两件事，
   不能互相替代。

4. **只在一台机器上实测过**。macOS、纯 Windows、老 JDK 8 都**没有真正跑过**。

5. **指纹只能发现"变化"，不能发现"一直就错"**。`baseline.txt` 是在当时认为正确的版本上生成的。
   假如电路本身就有错，指纹只会忠实地把这个错误一直保留下去 —— 所以它防的是"改坏"，
   不是"本来就没做对"。
